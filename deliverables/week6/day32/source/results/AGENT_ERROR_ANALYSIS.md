# Agent 错误模式分析报告

## 1. 实验范围

本报告分析 Day31 checkpoint-38 在 40 条开发集上的 Agent 轨迹。对照组使用 main Prompt，实验组只增加一条 input-fidelity 规则。两组共享相同模型、adapter、工具、知识库、题目、成功谓词、确定性生成参数和最大 6 步限制。

最终测试集未用于 Prompt 选择，避免按测试结果挑选配置。

## 2. 分类方法

每个失败案例可拥有多个标签，但只按固定优先级分配一个主要标签：格式解析 → 死循环 → 选错工具 → 参数提取 → 工具错误未处理 → 过早回答 → 最终答案错误 → Observation 幻觉 → 未知错误。

因此“主要标签数量”之和等于失败案例数；“标签总出现数”允许一条轨迹被多个规则命中。

## 3. Main Prompt 失败统计

40 条中 18 条严格通过、22 条失败；input-fidelity ablation 通过 14 条。两组死循环为 0。

| 错误类型 | 主要标签 | 标签总出现数 |
|---|---:|---:|
| 选错工具 | 0 | 3 |
| 参数提取错误 | 1 | 4 |
| 死循环 | 0 | 0 |
| 工具错误未处理 | 0 | 0 |
| 过早回答 | 0 | 0 |
| 最终答案错误 | 17 | 22 |
| Observation 幻觉 | 0 | 0 |
| 格式解析错误 | 4 | 4 |

最主要的问题不是工具完全不可调用：工具 schema 合法率和 Observation 完整性均为 100%，无循环率也为 100%。瓶颈集中在最终回答语义与 Observation 对齐，以及少量工具调用格式、路由和参数错误。

## 5. 根因分析

1. **最终答案约束不足。** 多数失败轨迹完成了合法工具调用，但最终文本没有精确复述工具返回的值、状态或风险节点，导致语义正确与可溯源检查失败。
2. **自然语言规则存在竞争。** input-fidelity 规则提升了部分路由与参数指标，但让模型更关注复制输入，弱化了最终回答中对 Observation 的完整表达。
3. **格式稳定性仍有限。** 4–6 条轨迹包含不可接受的工具调用格式，说明仅靠 Prompt 无法完全保证结构化输出稳定。
4. **安全终止较稳定。** 两个 Prompt 均未出现死循环；工具错误后的安全终止率为 95%–100%。

## 6. 代表案例解释

- `dev-knowledge-003`：ablation 使输入实体保持更稳定，案例由失败转为通过。
- `dev-calculator-003` 与 `dev-calculator-007`：工具路由并非主要问题，最终数值表达与预期语义不一致造成回归。
- `dev-code-004`：AST 检查结果需要在最终回答中准确引用；ablation 后格式/表述未满足全部检查。
- `dev-recovery-002` 与 `dev-recovery-005`：错误状态需要清晰终止并解释，不应继续生成模糊结论。

逐题实际序列、失败检查和标签见 `main_error_cases.csv`、`ablation_error_cases.csv` 及两份分析 JSON。

## 7. 选择结论

最终采用 main Prompt。选择依据是开发集严格成功率与语义正确率，而不是单独追求首工具或参数指标。input-fidelity ablation 作为单因素实验完整保留，但不进入最终组合。

后续提升应优先使用结构化解码或输出校验器保证工具调用格式，并针对“Observation → 最终回答”构造更丰富的监督样本；不应继续无边界叠加自然语言规则。

## 8. 限制

- 40 条开发集适合定位失败模式，不足以证明统计显著性；
- 失败标签来自预定义自动规则，边界案例仍需人工审阅；
- 本报告只比较一个 Prompt 因素，不能把全部能力差异归因于该条规则；
- 最终测试结果在 Day31/Day33 中独立报告，不参与本日选择。
